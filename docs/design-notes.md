
# Skein Design System

**Skein** is a personal knowledge-graph tool: it merges scattered AI chat history (Claude, ChatGPT, etc.) into a single contradiction-aware graph of atomic claims, then uses that graph — not raw transcripts — as the retrieval layer for RAG. Repeated, evolving conversations on one topic get consolidated into a navigable structure of decisions, facts, and open questions, with superseded claims chained rather than overwritten (see the worked Postgres → MongoDB → Postgres example in the project brief).

Zero-infrastructure, fully client-side: React + Vite, IndexedDB storage, Cytoscape.js for graph rendering, WebLLM for default in-browser extraction with optional BYOK for sharper quality, hosted on GitHub Pages. Sits in the same family as the author's other shipped client-side tools (LoopLens, Reality Check, Singularity, Parlance, Claude-Batch).

**Sources given for this design system:** a project brief (`Skein — Project Brief`, pasted in full at design-system creation time — no external doc link) and two logo files, `uploads/Skein Logo.png` / `uploads/Skein Logo.svg`. No Figma file, codebase, or existing UI screens were provided — every screen in `ui_kits/` is an original design built to the brief's palette, type, and "graph visual language" spec, not a recreation of an existing product.

## Content fundamentals

- **Voice:** technical, precise, a little dry. Skein talks about itself the way a well-commented codebase would — no hype, no exclamation points. "Nothing is overwritten," "correction supersedes Mongo, not the original Postgres claim" is the register: declarative, causal, exact.
- **Person:** second person for UI copy and instructions ("paste a transcript," "your claim graph"); the brief itself narrates in third person about "the person" / "a user" when explaining the concept in the abstract.
- **Casing:** sentence case everywhere — titles, buttons, nav labels. Never title case, never all-caps for prose. The one deliberate all-caps convention is the bracketed status tag (`[ACTIVE]`, `[SUPERSEDED]`, `[CORRECTION · CURRENT]`) — reserve caps for these system tags only, so they read as machine state, not emphasis.
- **Terminology is exact and consistent:** "claim" (never "note" or "message"), "supersede" (never "replace" or "overwrite"), "chain" (never "thread" — thread is reserved for the visual edge motif), "cluster" (never "group" or "category"). Reuse the brief's own vocabulary verbatim; it was chosen carefully (skein = "a tangled thread you organize").
- **Numbers and data read as data:** hop counts, timestamps, and confidence read in monospace, framed like a CLI result: `3 hops · chain · current: Postgres`.
- **No emoji.** No decorative icons standing in for words. The one permitted symbolic flourish is the off-center gold dot on the wordmark's "i" — everything else is restrained.
- **Example copy voice:** query placeholder `why postgres?`; empty state `no claims yet — paste a transcript to get started`; a superseded node's caption `superseded 6:02pm — mongo made relational queries harder`.

## Visual foundations

- **Palette:** dark, warm, low-saturation base (`#353535`) with three warm accents — bronze `#B2945B` (correction/selection), gold `#DECD87` (active/primary, also the wordmark dot), pale gold `#E9DDAF` (glow/highlight/hover) — against cream text `#FFF9F0`. A single cool color, slate blue-grey `#56626C`, is reserved exclusively for superseded/dead claims so "alive vs. dead" is legible by hue alone, not just opacity. Max two background values in any composition: base dark surface + one raised/sunken variant.
- **Type:** two-family system. Display/wordmark is a bold serif (Century Bold in the original mark; substituted with **PT Serif Bold** for web — see Font substitution below) used sparingly, for the wordmark and page-level headings only. IBM Plex Sans carries all UI text (labels, body, buttons). IBM Plex Mono is reserved for anything that is *data*: timestamps, tags, hop counts, the query bar, node IDs — mono signals "this is a machine value," not prose.
- **Signature detail:** the wordmark's "i" is dotless by design, with a hand-placed gold dot sitting slightly off-center — the one intentional imperfection in an otherwise restrained system. Never re-center it or recreate it as a perfect circle-over-stem default "i."
- **Spacing:** 4px base scale (4/8/12/16/20/24/32/40/48/64/80). Generous whitespace around graph canvas; tighter, denser spacing inside the sidebar and query bar (data-dense contexts read in mono at smaller sizes).
- **Corner radii:** two scales now coexist. Flat/technical elements (badges, hairline dividers where they remain) stay small — 4px tags. Soft-molded neumorphic chrome (cards, buttons, inputs, filter rows) uses a larger, deliberately un-sharp scale — 12px small controls, 18px cards/panels, 26px large surfaces — because neumorphism needs room for its shadow curvature to read. Nodes/knots stay circular, never rounded-rect.
- **Cards & panels — neumorphism (the system's tactile layer):** structural chrome (Card, Button secondary/ghost, Input, QueryBar, ClusterFilter rows) is soft-molded: the surface is the *same tone* as what it sits on (`--surface-raised` on `--surface-base`), shaped only by a dual shadow — a dark facet (`rgba(0,0,0,.45)`) and, in place of the usual white highlight, a **warm gold-tinted highlight facet** (`rgba(233,221,175,.07)`, drawn from `--color-gold-pale`) so the soft-UI language still reads as Skein's own rather than generic light-mode neumorphism. Raised elements (`--shadow-neu-raised`) read as resting above the surface; recessed ones (`--shadow-neu-inset`) read as pressed into it — text inputs and the query bar are always inset grooves (you're typing "into" the graph), buttons and cards are always raised, and buttons physically press into their inset shadow on click (with a slight scale-down). Selected cluster-filter rows show the same pressed/inset state as an active toggle. Bracket status badges and graph knots/threads deliberately opt out of neumorphism — they keep their own flat-text and radial-gradient languages so machine-state (`[ACTIVE]`) and the graph itself stay visually distinct from UI chrome.
- **Backgrounds:** solid flat color as the default surface, with restrained warm-toned gradients used the way Claude's own product does — as atmosphere and emphasis, never as decoration. A soft radial gold glow (`--gradient-hero`) sits behind hero moments (the ingest screen's headline); active/glowing knots get a soft radial halo behind them (`--gradient-glow-gold` / `--gradient-glow-bronze`) rather than a flat drop-shadow alone; the primary and correction buttons use a subtle two-stop linear gradient fill (`--gradient-primary`, `--gradient-correction`) instead of flat color; sidebar/panel surfaces may use a barely-there vertical gradient (`--gradient-surface`) for depth. Every gradient stays within one hue family (gold→pale-gold, bronze→gold) at low opacity — never a loud multi-hue or cool-to-warm gradient, and never on body text or large flat fields. No photographic imagery, no textures/patterns, no illustration style — the graph itself is still the primary non-flat visual content.
- **Animation:** minimal and functional everywhere except the graph itself, where nodes get a slow, gentle vertical float (independent per-node delay, ~3.5–4.5s ease-in-out) so the canvas reads as alive/responsive rather than static — never bouncy or spring-like, just a slight organic drift. Active threads pulse opacity subtly in sync with their glow. Hover on a knot scales it up (~1.12–1.14×) and brightens it; UI chrome elsewhere (buttons, panels) uses the standard ease `cubic-bezier(.4,0,.2,1)`, fast (120ms) for hover/press feedback, base (200ms) for panel/modal transitions.
- **Hover/press states:** hover brightens toward pale gold (`--accent-primary-hover`) on interactive/active elements, or lightens border/background by one step on neutral controls — never a full hue shift. Press states are a slight scale-down (~0.97) plus a touch more brightness, never a color inversion.
- **Glow vs. fray → raised vs. sunk:** the core "alive vs. dead" visual grammar, now expressed through neumorphism itself rather than a glow effect. Active/correction claims are matte marble knots that sit raised above the surface, with a soft blurred contact shadow selling the physicality (only the faintest hint of sheen — never glossy). Superseded claims sink flush into the surface as dull, shallow-set marbles — no shadow lift, no shine. Threads follow the same logic: active threads are carved grooves (dark trench + thin highlight rim + a faint warm rim glow along the channel); superseded threads are the same groove rendered shallow and dashed. "Alive" literally stands up off the page; "dead" settles into it. Knots also react to the cursor — nearby nodes nudge subtly away as it passes, like marbles disturbed on the surface, rather than idly bobbing.
- **Cluster density:** high-connectivity claims render as raised, matte marble knots — grouped clusters of small unlabeled satellite claims sink as tiny matte pits into the surface around them, read by proximity/color rather than explicit connector lines. Only primary hub-to-hub relationships render as explicit carved-groove threads (see `guidelines/brand-cluster-density.html`). Reinterprets the density/mass of Graphify's community graphs in Skein's own warm gold/bronze/slate palette and marble/groove motif, not a copy of its UI chrome or navy palette.
- **Topic vs. status — two independent channels:** at mind-map scale, hue distinguishes *what a claim is about* (topic/subject), while elevation and finish distinguish *its state* (alive/dead/corrected) — the two never conflict. Each topic cluster gets its own muted hue from an extended palette (clay, moss, dusk-plum, muted teal, ochre, alongside the core gold) — all kept within the same low-saturation, warm-neutral value range as gold/bronze so new topics never read as a jarring rainbow. Status rides on top of hue, not instead of it: superseded claims desaturate to slate-grey and sink flush regardless of topic (a claim literally loses its color as it dies); a correction gets a thin bronze ring around its topic-hued marble rather than recoloring it. This keeps the reserved status colors (gold=active, bronze=correction, slate=dead) meaningful across an unlimited number of topics.
- **Transparency/blur:** used sparingly — a light `backdrop-filter: blur()` on modal/overlay scrims only, so the graph is legible but backgrounded. Not used for cards or panels in normal flow.
- **Imagery:** none in the brief; the brand has no photography direction. Do not introduce photographic or illustrative imagery — the visual identity is entirely typographic + graph-diagrammatic.

**Font substitution flag:** the brief specifies **Century Bold** for the wordmark, pending real licensing, and names **PT Serif Bold** as the intended web substitute. This system ships PT Serif Bold as the live display font (via Google Fonts) exactly as instructed. If/when licensed Century webfonts are available, drop the `.woff2` files into a new `tokens/fonts/` directory, add `@font-face` rules there, and repoint `--font-display`.

## Iconography

The brief defines no icon system, icon font, or SVG set — Skein's visual language is typographic and graph-diagrammatic (knots + threads), not icon-driven. Where a UI affordance needs a glyph (close, expand, search, chevron), this system substitutes **Lucide** icons (CDN: `unpkg.com/lucide-static`), chosen for its thin, geometric single-weight stroke that matches the system's restrained, technical feel. This is a substitution, not a brief-defined choice — flagged here per design-system policy. No emoji are used anywhere. No unicode glyphs are used as icons, except the literal `$` prompt character in the query bar, which is typographic (mono text), not iconographic. Bracketed status tags (`[ACTIVE]`, `[SUPERSEDED]`) function as Skein's actual "icon system" for state — text, not glyphs, by design.
